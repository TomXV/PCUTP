# PCUTP セッション設計 — 確立・維持・切断

本書は PCUTP のセッション層、すなわち「いつ接続が始まり、どうやって生きていることを
確かめ、どうやって終わるか」を扱う。ファイルの転送そのもの（META / DATA / ACK /
DONE）は [PCUTP-0.1.md](PCUTP-0.1.md) の 8〜18 節に譲る。

対象は現行実装（`src/pcutp/{server,client,link}.py` および `picocalc/PCUTP.BAS`）。
ワイヤ上のバージョン文字列は `PCUTP/1` のまま変わらない。

第 7 節は**提案**であり、まだ実装されていない。

---

## 1. 前提 — UART には「接続」が無い

TCP と決定的に違うのは、線の上に接続という状態が存在しないことである。
ソケットが閉じたことを OS が教えてくれることもなければ、RST が返ってくることもない。

PCUTP から見えるのは 2 つだけである。

- 線の上を流れてきたバイト列
- 何も流れてこない時間

そして**「健全なリンクの沈黙」と「死んだリンクの沈黙」は、受信側から区別できない。**
セッション層の設計は、ほぼこの一点への対処に費やされている。

## 3. 確立 — なぜ 3 ウェイか

`SYNC` は一見冗長に見える。`HELLO` に対して `CONNECT` を返せば済むように思える。

しかし `SYNC` が無い場合、送信側は**受信側が生きている確証を持たないまま** `CONNECT` を
投げることになる。1 節の通り UART には接続の概念が無いので、「自分の応答が相手に届いた」
を知る手段は、相手がそれに応答することだけである。

各行の役割は次の通り。

| 行 | 発行元 | 意味 |
|---|---|---|
| `HELLO PCUTP/1` | 受信側 | 呼び出し。バージョンを名乗る |
| `HOWRU` | 送信側 | 応答トーン。「聞こえている」 |
| `SYNC` | 受信側 | 「あなたの応答が私に届いた」＝双方向の確認 |
| `CONNECT <baud> MAXBLK=<n>` | 送信側 | キャリア確立。転送パラメータを通知 |

`CONNECT` の前に 0.4 秒の間 (`CONNECT_DELAY`) を置くのは、ダイヤルアップの
ネゴシエーション音を模した演出であり、プロトコル上の必然性は無い。

バージョンが合わない場合、送信側は `ERR VERSION` を返して IDLE に戻る。

## 4. `FETCHING` — 沈黙に名前を与える

v0.2 で追加された中で最も効いている 1 行である。

`GET` を受けた送信側は、インターネットからファイルを取得する。この間、線の上には
何も流れない。最大 30 秒 (`HTTP_TIMEOUT`)。

```
  GET ─────▶
              ← ここで最大 30 秒、完全な沈黙
  「切れた？」 ← 受信側のリンク断タイマ (15 秒) が誤発火する
```

1 節で述べた通り、この沈黙は死んだリンクと区別できない。`FETCHING` は
「まだいる。いまインターネット側にいる」の宣言であり、これを受けた受信側は
続く `META` を待つ窓を 15 秒から 45 秒へ広げる。

**不変条件: `FETCH_TIMEOUT` (45s) > `HTTP_TIMEOUT` (30s)**

`picocalc/PCUTP.BAS` の `FETTMO` と `KATMO` にも同じ関係が要る。これが崩れると、
取得が受信側の忍耐より長生きし、**正常な転送がリンク断に見える**。

なお `FETCHING` を送らない旧実装とも互換である。受信側は `FETCHING` が来なければ
そのまま `META` を待つ。

## 5. 維持 — キープアライブは制御層より下にいる

`PING` / `PONG` は `Link.recv_line` の内側で透過的に処理され、上位のステートマシンには
一切見えない。

```
   server.py / client.py     ← ACK を待つコードは ACK のことだけ考えればよい
   ─────────────────────
   link.py                   ← PING を見たら PONG を返し、上には渡さない
   ─────────────────────
   transport.py
```

これは単なる整理ではない。もし `PONG` が上位に漏れると、ブロックの `ACK` を待つ
ループが `PONG` を「予期しない応答」として扱ってしまう。転送中に生存確認が走る以上、
この分離は必須である。

| 定数 | 値 | 意味 |
|---|---|---|
| `KEEPALIVE_INTERVAL` | 5.0s | この時間無音なら `PING` を送る |
| `KEEPALIVE_TIMEOUT` | 10.0s | この時間何も受信しなければ `LinkLostError` |

受信側 (`PCUTP.BAS`) では、URL 入力プロンプト中も `InputAlive$` が `PING` に応答し続ける。
ユーザーがキーを打っている間にリンクが落ちたと誤判定されないためである。

## 6. 切断 — 現行方式とその不足

現行は 1 行で終わる。

```
  受信側 → CLOSE
  送信側 : ログに記録し、IDLE へ戻る
```

受信側は `CLOSE` を送った 200ms 後に「Disconnected」と表示して終了する。
これは動作するが、次の 4 点が欠けている。

**(a) 確認応答が無い**
`CLOSE` が届いたという証拠が無い。取りこぼされた場合、送信側は
`--idle-timeout`（既定 3600 秒）までポートを掴んだまま待ち続ける。

**(b) 片方向しか閉じられない**
閉じられるのは受信側だけである。デーモンを Ctrl-C で止めた場合、送信側はただ黙るので、
受信側は 10 秒後にキープアライブの失敗としてそれを知り、**「Link lost」と表示する。
正常な終了が障害として報告される。**

**(c) ハーフクローズが無い**
「もう新しい要求は出さないが、いま送っているファイルは最後まで受け取る」を
表現する手段が無い。

**(d) 静穏期間が無い**
`CLOSE` を送った瞬間に線は空いたものとみなされる。飛行中だったもの——遅れて届いた
`ACK`、ブロックの末尾——は**次のセッションの入力に落ち、その最初の制御行として読まれる。**

(d) は理論上の懸念ではない。レートネゴシエーションの実装時、同じ理屈で
`RATE 230400 TEST` が `RARATE 230400 TEST` として読まれ、セッションが壊れた実例がある。

## 7. 提案 — TCP の FIN に倣った切断

### 7.1 語彙

新語は 1 つだけである。

| 語 | 方向 | 意味 |
|---|---|---|
| `CLOSE` | どちらからでも | **FIN**「私はこれ以上何も送らない」（既存語。今後は応答を伴う） |
| `BYE` | どちらからでも | **FIN-ACK**「受け取った。あなたからは何も期待しない」（新規） |
| `ERR …` + 切断 | どちらからでも | **RST 相当**。秩序ある終了を諦める（既存の挙動） |

TCP と同じく、**片方向ずつ独立に閉じる**。`CLOSE` は「私の送信は終わり」であって
「セッションを終わりにしろ」ではない。

### 7.2 完全な切断

```
   A                                             B
   │                                             │
   │  CLOSE   ──────────────────────────────────▶│   A は送信を終えた（ハーフクローズ）
   │                                             │
   │◀──────────────────────────────────────  BYE │   B は受領。まだ作業を続けてよい
   │                                             │
   │              （B が飛行中の作業を完了）      │
   │                                             │
   │◀────────────────────────────────────  CLOSE │   B も送信を終えた
   │                                             │
   │  BYE     ──────────────────────────────────▶│
   │                                             │
   ├──────────── LINGER 2秒 ─────────────────────┤   双方、再送された CLOSE には
   ▼                                             ▼   BYE を返し続ける
  IDLE                                          IDLE
```

**通常のケース**（受信側が URL プロンプトにいて、飛行中の作業が無い）では、B は
`BYE` の直後に自分の `CLOSE` を送る。行指向プロトコルなので 2 行を連続して出すだけで、
特別な合成語は要らない。

```
   A: CLOSE  ─────▶
      ◀─────  BYE
      ◀─────  CLOSE      ← 間を置かず続けて
   A: BYE    ─────▶
```

### 7.3 ハーフクローズが効く場面

現行の受信側は、何も飛行していない時にしか `CLOSE` を送らない。したがって
ハーフクローズが真に効くのは**送信側から閉じる場合**である。

```
   PicoCalc                                      uConsole
   │                                             │
   │            ◀─────── DATA 42 4096 …          │   転送中に Ctrl-C
   │  ACK 42    ───────▶                         │
   │            ◀─────── CLOSE                   │   「新しいファイルはもう無い」
   │  BYE       ───────▶                         │
   │            ◀─────── DATA 43 4096 …          │   いま送っている分は最後まで
   │  ACK 43    ───────▶                         │
   │            ◀─────── DONE <CRC32>            │
   │  OK <CRC32>───────▶                         │
   │  CLOSE     ───────▶                         │   受信側も終わり
   │            ◀─────── BYE                     │
```

これにより **(b) と (c) が同時に解ける**。デーモンの終了が「Link lost」ではなく
「Disconnected」として表示され、しかも進行中のファイルは失われない。

### 7.4 状態

| 状態 | 意味 | 遷移 |
|---|---|---|
| `CONNECTED` | 通常 | `CLOSE` 送信 → `FIN_SENT` / `CLOSE` 受信 → `CLOSE_WAIT` |
| `FIN_SENT` | 自分は送信終了、応答待ち | `BYE` 受信 → `FIN_ACKED` |
| `FIN_ACKED` | 自分は閉じた。相手はまだ | `CLOSE` 受信 → `BYE` を返して `LINGER` |
| `CLOSE_WAIT` | 相手は閉じた。自分はまだ作業中 | 作業完了 → `CLOSE` 送信 → `LAST_ACK` |
| `LAST_ACK` | 自分も閉じた。最後の応答待ち | `BYE` 受信 → `LINGER` |
| `LINGER` | 静穏期間 | 2 秒無音 → `IDLE` |
| `IDLE` | セッション無し | `HELLO` 受信 → `CONNECTED` |

同時クローズ（双方が同時に `CLOSE` を送る）は特別扱いを要しない。
**どの状態であっても `CLOSE` を見たら `BYE` を返す**、という規則だけで正しく収束する。

### 7.5 タイマ

| 定数 | 提案値 | 役割 |
|---|---|---|
| `CLOSE_TIMEOUT` | 3.0s | `BYE` を待つ時間 |
| `CLOSE_RETRIES` | 3 | `CLOSE` の再送回数。尽きたら諦めて切断 |
| `LINGER_TIME` | 2.0s | 最後の `BYE` 後、線を見張る時間 |

`LINGER_TIME` の根拠: この線で飛行しうる最大のものは 1 ブロック（4096 バイト）であり、
115200 baud で約 0.36 秒である。2 秒はその 5 倍以上の余裕がある。

### 7.6 取りこぼしたときの挙動

| 失われた行 | 結果 |
|---|---|
| `CLOSE` | 送出側が `CLOSE_TIMEOUT` で再送。最大 3 回で相手に届く |
| `BYE` | 送出側が `CLOSE` を再送。相手は `LINGER` 中なので `BYE` を返し直す |
| 双方を繰り返し | 3 回で諦めて切断。相手はキープアライブ (10s) でリンク断を検出。**現行と同じ挙動に退化するだけで、悪化はしない** |

`BYE` は冪等である。同じ `CLOSE` に何度 `BYE` を返しても問題ない。これが
シーケンス番号を持たないプロトコルにおける再送耐性の担保となる。

### 7.7 TCP から意図的に取らないもの

- **シーケンス番号**: 制御行に番号が無いため、重複した `CLOSE` と新しい `CLOSE` を
  区別できない。`LINGER` と `BYE` の冪等性がその代替である。
- **2×MSL の TIME_WAIT**: 滞留させるネットワークが存在せず、線の飛行時間は有界である。
  2 秒で十分。
- **ハーフオープン検出**: キープアライブ (5 節) が既に担っている。
- **TIME_WAIT を能動的閉塞側のみに置く設計**: TCP ではポート/ISN の再利用が理由だが、
  PCUTP の `LINGER` は**次セッションの最初の 1 行を守る**ためにある。線は 1 本を
  双方が読むので、**両端に置く必要がある**。

### 7.8 互換性

ワイヤバージョンは `PCUTP/1` のまま変えない。新旧が混ざっても破綻しない。

- **旧受信側 × 新送信側**: 旧受信側は `CLOSE` を送った直後にポートを閉じる。
  新送信側が返す `BYE` は誰も読まないまま捨てられる。無害。
- **新受信側 × 旧送信側**: 旧送信側は `BYE` を返さない。新受信側は `CLOSE` を
  3 回再送したのち諦めて切断する。現行より遅いが、結果は正しい。

### 7.9 実装が触る場所

| 場所 | 変更 |
|---|---|
| `server.py` `serve_once` の `CLOSE` 分岐 | `BYE` を返し、飛行中の作業を終えてから自分の `CLOSE` を送る |
| `server.py` SIGINT ハンドラ | 即座に落ちるのではなく `CLOSE` を送出する |
| `client.py` `close()` | `BYE` を待ち、相手の `CLOSE` に `BYE` を返し、`LINGER` する |
| `link.py` | `LINGER` 中は `CLOSE` 以外を捨てる読み取りモード |
| `PCUTP.BAS` 空 URL の分岐 | 同上。`RecvLine$` に静穏読み捨てを追加 |
| `const.py` | `CLOSE_TIMEOUT` / `CLOSE_RETRIES` / `LINGER_TIME` |

## 9. 付記 — 回線速度ネゴシエーションについて

v0.2 の開発中、`RATE` / `PROBE` による回線速度の自動ネゴシエーション（低速から順に
実測し、最も効率の良いレートを採用する方式）を実装したが、**廃止した。**

実測で優位が確認できなかったことが理由である。ただし当時の計測は、同一のシリアル
ポートを 2 つのプロセスが同時に開いていた状態で行われており、データが汚染されていた
可能性がある。将来この機能を再検討する場合は、**ポートの排他を確認したうえで
測り直すこと**。設計そのものは `RATE <baud> CAN?` / `YES` / `GO` / `TIME <ms>` /
`FAIL` / `LOCK` という送信側主導の形に到達しており、git 履歴から参照できる。
