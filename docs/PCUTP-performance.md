# フロー制御・MTU・圧縮の実機評価

2026-09-07開始の作業。PicoCalcのCore GP4/GP5（COM2）とFlipper LunaxのUARTブリッジを
115200 baud・8N1で接続。コンソールは別のUSBシリアル経由。
基準実装は `9b2cca4`。変更後は [フロー制御・圧縮拡張](PCUTP-flow.md) を使用した。

## 結果

**無圧縮の1 MiB転送は124.84秒から94.01秒へ短縮（速度1.328倍、時間24.7%減）。**
変更後は10.89 KiB/sで、115200 8N1のペイロード理論上限11.25 KiB/sの96.8%に達した。
この比較は両方式とも4096バイト、1回ずつの長時間確認。小さいファイルでは各条件3回測定した。
自然発生の再送は全成功試行で0、ブロックCRC・展開後のファイルCRCは一致した。

## 1. 以前の「約2倍」という見積もりの修正

前の記録では32 KiB転送の表示・完了演出を含む時間から約5.5 KiB/sと見積もっていた。
今回はMETA送信から最終OK受信までを計時し、音や切断待ちを分離した。
この基準では現行方式も約8 KiB/sであり、115200 baudのままで2倍にはならない。
無圧縮の実測改善率は約1.3倍。圧縮時の速度は**展開後のファイル容量／時間**なので、
11.25 KiB/sを超える場合も回線速度そのものを超えたわけではない。

## 2. MTUとフロー制御

32 KiB・各3回の中央値。圧縮なし。

| MTU | 従来: 窓1 | 新方式: 窓2 |
|---:|---:|---:|
| 256 | 6.27 KiB/s | 7.14 KiB/s |
| 512 | 7.40 KiB/s | 10.21 KiB/s |
| 1024 | 7.64 KiB/s | **10.35 KiB/s** |
| 2048 | 7.87 KiB/s | 10.34 KiB/s |
| 4096 | 8.01 KiB/s | 10.14 KiB/s |

128 KiB・窓2・各3回の中央値。圧縮なし。

| MTU | 実効速度 |
|---:|---:|
| 1024 | 10.680 KiB/s |
| 2048 | **10.768 KiB/s** |
| 4096 | 10.713 KiB/s |

最大MTUが常に最速ではない。小さいファイルでは最後のブロックを処理する時間が目立ち、
大きいファイルではヘッダ数の少なさが効く。今回の候補間では差が小さい領域もある。
自動選択はこの測定に合わせたコストモデルで、32 KiB→1024、128 KiB→2048、
1 MiB→4096とする。あらゆるMTU・回線・データの全探索による絶対最適値とは主張しない。
256/512も最終版で各3回追加測定し、32 KiBでは1024を超えなかった。

## 3. 圧縮の追加効果

窓2・MTU自動選択で各3回。以下は**GET受信からOKまでの中央値**で、
圧縮可否の事前判定も含む。HTTP取得はローカルの同一バイト列に置き換えた。
uConsoleの音を有効にした状態で測定した。

| ファイル | 元サイズ | 圧縮無効 | 圧縮自動 | 追加の速度改善 |
|---|---:|---:|---:|---:|
| BASICソース | 27,242 B | 2.585秒 | 2.511秒 | 約3.0% |
| turrican.mod | 41,364 B | 3.868秒 | 3.419秒 | 約13.2% |
| gzip済みソース | 10,045 B | 1.046秒 | 1.048秒 | ほぼ同じ（約0.2%遅い） |
| 固定seedの乱数 | 131,072 B | 11.893秒 | 11.888秒 | ほぼ同じ |

BASICは1024バイトMTUのまま5ブロックだけ圧縮、MODは圧縮可能性の判定により
4096バイトMTUを選び4ブロック圧縮。表は圧縮とMTU選択を合わせた最終設定同士の比較。
gzip・乱数は圧縮ブロック0で通常DATAへ自動退避し、転送量を増やさなかった。
初期実装でgzipの事前判定に約25msかかったため、小さいサンプルで繰り返しを判定し、
無駄な圧縮試行を省くよう修正した。

繰り返しを含む人工データ32 KiBでは、8ブロックすべてをLZ4化し、DATA系の線上量は
3,328バイト、1.537秒、**20.82 KiB/s**（1回測定）。圧縮なしの同じ4096バイトMTUの
約10.14 KiB/sに対して約2.05倍だった。これは圧縮しやすいデータの例であり、
BASIC・MOD・画像等にも同じ倍率が出るという意味ではない。

## 4. 故障を入れた実機試験

- 無圧縮DATAのseq=1を破損: バリア1回、2ブロック再送、最終CRC一致。
- 圧縮ZDATAのseq=1を破損: バリア1回、2ブロック再送、展開後の最終CRC一致。
- 最後のACKを送信側で1回破棄: バリア1回、データ再送0、最終CRC一致。
  既定のACKタイムアウト5秒分は増加する。

Pythonでは境界サイズ、窓の上限、能力制限、ACK重複・欠落、DATA重複・欠落、
再送バリア応答の重複・欠落、再送上限、未送信番号へのACK、圧縮・非圧縮混在、
不正圧縮入力を検証した。LZ4は独立したliblz4実装とも相互にデコードして照合した。

## 5. 音のリアルタイム性と音切れ

最初の音声実装は長いPCMをFIFOと再生パイプに溜めていたため、実際の通信状態から
遅れて音が鳴った。FIFOを廃止し最新イベントを優先、10ms単位で音声を供給した。
次に短すぎる再生開始しきい値と波形切り替えによる音切れを修正した。

- サンプル位置は時刻の丸め直しでなく連続したカウンタで進め、位相飛びを防ぐ。
- 切り替えに5msのクロスフェードを入れ、古い音は後で再生しない。
- ALSAバッファ60ms・開始しきい値30ms・周期10ms。音声は通信と別スレッド。
- ALSAのunderrun数とイベント→レンダラの最大遅延を記録する。

修正版の乱数128 KiB転送3回ではALSA underrunはすべて0、レンダラまでの最大遅延は
9.6〜11.5msだった。スピーカーの音響遅延や主観的な音質まで計測した値ではない。

## 6. 測定データと再実行

[各試行のJSON](benchmarks/2026-09-07/) に時間、CRC、MTU、再送数、圧縮ブロック数、
DATA系の送信バイト数を保存した。後半の音声試験にはレンダラ遅延とunderrun数も含む。
音の修正は段階的に行っており、古い測定に新しい音声実装の結果を遡って付与していない。
[入力のサイズとSHA-256](benchmarks/2026-09-07/fixtures.json) も記録した。

生成データは `bytes((i*31 + i//256 + 7) % 256 for i in range(size))`。
乱数はPython 3.13の `random.Random(20260907).randbytes(131072)`。
gzipはBASICサンプルに `gzip.compress(data, mtime=0)` を適用した。
BASICサンプルは開発途中のLF版で、現在のCRLF版ソースとはハッシュが異なる。

```bash
PYTHONPATH=src .venv/bin/python scripts/hardware_benchmark.py \
  --program B:/PCFAST.BAS --window 2 --blocks 1024,2048,4096 \
  --size 131072 --repeat 3 --compression off --output /tmp/mtu.json

PYTHONPATH=src .venv/bin/python scripts/benchmark_suite.py \
  --basic /tmp/sample.bas --mod /path/to/sample.mod \
  --gzip /tmp/sample.gz --random /tmp/random.bin --output-dir /tmp/pcutp-results
```

UARTポートは排他オープンとし、別のデーモンと同時に読む状態を避けた。
固定115200 baudでの改善を対象とし、ボーレート引き上げ、転送再開、ハードウェアRTS/CTSは
今回の範囲には含めない。フロー制御・圧縮の利用に新しい配線は不要。

## 7. 配置と検証状態

最終BASICは `B:/PCUTP.BAS` に配置し、旧版は `B:/PCUTP20.BAK` に保存した。
Pythonは134テスト、ruff、65536バイトを2回転送するセルフテスト、wheel/sdistビルドが成功。
全22制御語の個別試聴もALSA underrun 0で完了した。

生成データ32 KiBをMTU自動・圧縮ありで転送し、1.531秒・20.90 KiB/s、再送0、
CRC一致を確認した。音声レンダラ最大遅延9.03ms、ALSA underrun 0。
